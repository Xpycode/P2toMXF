## Executive Summary

P2toMXF is a well-structured macOS application for converting Panasonic P2 video card footage to industry-standard MXF/MOV formats. The codebase demonstrates solid architecture with clear separation of concerns, but has several areas requiring attention, particularly around **Swift 6 concurrency safety**, **memory management in long-running processes**, and **error handling consistency**.

## Critical Issues (Priority: High)

### 1. Swift 6 Concurrency Violations

#### 1.1 `@unchecked Sendable` in Process Wrappers

**Location:** `FFmpegWrapper.swift:470-485`, `BMXWrapper.swift:155-170`

```swift
private final class OutputCollector: @unchecked Sendable {
    private let lock = NSLock()
    private var _output = ""
    // ...
}
```

**Issue:** While the implementation uses `NSLock` for thread safety, marking as `@unchecked Sendable` bypasses compiler checking. If the lock discipline is ever violated, this creates undefined behavior.

**Recommendation:** Consider using `OSAllocatedUnfairLock` (macOS 13+) or restructure to use actors:

```swift
actor OutputCollector {
    private var _output = ""

    func append(_ string: String) {
        _output += string
    }

    var output: String { _output }
}
```

---

#### 1.2 Non-Sendable Capture in Process Handlers

**Location:** `FFmpegWrapper.swift:516-576`

```swift
errorPipe.fileHandleForReading.readabilityHandler = { [weak self] handle in
    // ...
    guard let self = self else { return }
    let metrics = self.parseFFmpegOutput(str)  // Captures non-Sendable self
```

**Issue:** `FFmpegWrapper` is not marked `Sendable`, yet it's captured in closures that execute on arbitrary threads. This is a Swift 6 concurrency violation.

**Recommendation:**
- Mark `FFmpegWrapper` as `@unchecked Sendable` if you can guarantee thread safety, or
- Refactor to pass only sendable data into handlers, or
- Convert to an actor

---

#### 1.3 MainActor Isolation Gaps in QueueManager

**Location:** `QueueManager.swift:1-20`

```swift
@MainActor
class QueueManager: ObservableObject {
    static let shared = QueueManager()
    // ...
}
```

**Issue:** While `QueueManager` is `@MainActor` isolated, the singleton pattern with `static let shared` can be accessed from any context. The `@MainActor` annotation only ensures methods are called on the main thread when called from async contexts, but synchronous access from background threads is still possible.

**Recommendation:** Ensure all access to `QueueManager.shared` is from `@MainActor` contexts, or use a pattern that enforces this:

```swift
@MainActor
static let shared = QueueManager()

nonisolated static func getShared() async -> QueueManager {
    await MainActor.run { shared }
}
```

### 2. Memory Leak Potential in Process Handlers

#### 2.1 Retain Cycles in File Handle Handlers

**Location:** `FFmpegWrapper.swift:516`, `BMXWrapper.swift:199`

```swift
errorPipe.fileHandleForReading.readabilityHandler = { [weak self] handle in
```

**Issue:** While `self` is weakly captured, the `OutputCollector` and other objects created before this closure may be strongly retained. Additionally, if the process never terminates (e.g., zombie process), these handlers persist indefinitely.

**Recommendation:** Always set `readabilityHandler = nil` in a cleanup block, not just in `terminationHandler`:

```swift
defer {
    errorPipe.fileHandleForReading.readabilityHandler = nil
    outputPipe.fileHandleForReading.readabilityHandler = nil
}
```

---

#### 2.2 Actor State Never Cleared

**Location:** `ThumbnailManager.swift:27-28`

```swift
private var cache: [UUID: ClipThumbnails] = [:]
private var pendingTasks: [UUID: Task<ClipThumbnails, Never>] = [:]
```

**Issue:** The cache grows unbounded. While `clearCache()` exists, it's only called when loading a new P2 card. If the user loads multiple cards without explicitly clearing, memory usage accumulates.

**Recommendation:** Implement an LRU cache with size limits:

```swift
private let maxCacheSize = 100
private var accessOrder: [UUID] = []

func getThumbnails(for clip: P2Clip) async -> ClipThumbnails {
    // ... existing logic ...

    // Evict oldest entries if cache too large
    while cache.count > maxCacheSize, let oldest = accessOrder.first {
        accessOrder.removeFirst()
        cache.removeValue(forKey: oldest)
    }
}
```

### 3. Error Handling Inconsistencies

#### 3.1 Silently Swallowed Errors

**Location:** `P2CardParser.swift:54`

```swift
for xmlFile in xmlFiles {
    if let clip = try? parseClipXML(at: xmlFile, contentsPath: contentsPath) {
        clips.append(clip)
    }
}
```

**Issue:** Parsing errors are silently ignored. If 15 of 16 clips fail to parse due to a file system issue, the user sees only 1 clip with no indication of the problem.

**Recommendation:** Collect and report errors:

```swift
var clips: [P2Clip] = []
var parseErrors: [(URL, Error)] = []

for xmlFile in xmlFiles {
    do {
        let clip = try parseClipXML(at: xmlFile, contentsPath: contentsPath)
        clips.append(clip)
    } catch {
        parseErrors.append((xmlFile, error))
    }
}

if !parseErrors.isEmpty {
    // Log or propagate partial error information
}
```

---

#### 3.2 Inconsistent Error Types Across Services

**Issue:** Different services define their own error enums:
- `FFmpegWrapper.FFmpegError`
- `BMXWrapper.BMXError`
- `P2CardParser.ParserError`
- `VerificationService.VerificationError`

While this is good for specificity, there's no unified error handling strategy. Some errors are `LocalizedError`, some include `.cancelled` cases, patterns vary.

**Recommendation:** Create a unified error protocol or base enum:

```swift
enum P2toMXFError: LocalizedError {
    case ffmpeg(FFmpegError)
    case bmx(BMXError)
    case parser(ParserError)
    case verification(VerificationError)

    var errorDescription: String? {
        switch self {
        case .ffmpeg(let e): return e.errorDescription
        // ...
        }
    }
}
```

### 5. Potential Bugs

#### 5.1 Race Condition in Cancellation

**Location:** `FFmpegWrapper.swift:624-643`

```swift
func cancelConversion() {
    isCancelling = true

    if let process = currentProcess, process.isRunning {
        // ...
        process.terminate()
    }

    currentProcess = nil
    bmxWrapper.cancel()
}
```

**Issue:** `isCancelling` is a plain `Bool` accessed from multiple threads. There's a race between setting `isCancelling = true` and checking it in `terminationHandler`. Additionally, `currentProcess = nil` happens before the process actually terminates.

**Recommendation:** Use atomic operations or actor isolation:

```swift
private let cancelLock = NSLock()
private var _isCancelling = false

var isCancelling: Bool {
    cancelLock.withLock { _isCancelling }
}

func cancelConversion() {
    cancelLock.withLock { _isCancelling = true }
    // ...
}
```

#### 5.2 Potential Deadlock in ThumbnailManager Semaphore

**Location:** `ThumbnailManager.swift:166-186`

```swift
private func acquireSemaphore() async {
    if activeExtractions < maxConcurrentExtractions {
        activeExtractions += 1
        return
    }

    await withCheckedContinuation { continuation in
        waitingContinuations.append(continuation)
    }
}
```

**Issue:** If all 3 slots are taken and more requests come in, they wait. But if the tasks holding slots are cancelled without calling `releaseSemaphore()`, waiting tasks block forever.

**Recommendation:** Use a proper async semaphore or add cancellation handling:

```swift
private func extractFrameWithSemaphore(from url: URL, atSeconds timestamp: Double) async -> NSImage? {
    await acquireSemaphore()
    defer { releaseSemaphore() }  // Always release, even on cancellation

    if Task.isCancelled { return nil }
    return await ffmpeg.extractFrame(from: url, atSeconds: timestamp)
}
```

#### 5.3 Security-Scoped Resource Imbalance

**Location:** `QueueManager.swift` (multiple locations)

```swift
guard job.cardPath.startAccessingSecurityScopedResource() else {
    // ...
}
defer {
    job.cardPath.stopAccessingSecurityScopedResource()
}
```

**Issue:** If the job fails or is cancelled before `defer` executes, the resource may remain accessed. Additionally, nested access (multiple clips from same card) can cause imbalance.

**Recommendation:** Track access state explicitly:

```swift
private var accessedResources: Set<URL> = []

func startAccessingIfNeeded(_ url: URL) -> Bool {
    if accessedResources.contains(url) { return true }
    if url.startAccessingSecurityScopedResource() {
        accessedResources.insert(url)
        return true
    }
    return false
}

func stopAccessingAll() {
    for url in accessedResources {
        url.stopAccessingSecurityScopedResource()
    }
    accessedResources.removeAll()
}
```

### 6. Performance Considerations

#### 6.1 Inefficient UI Updates During Conversion

**Location:** `FFmpegWrapper.swift:558-573`

```swift
DispatchQueue.main.async {
    progress(estimatedProgress, statusMsg)

    if let handler = metricsHandler {
        // ... build metrics ...
        handler(progressMetrics)
    }
}
```

**Issue:** Progress updates happen on every FFmpeg output line (potentially 25-60 times per second). This creates excessive main thread work.

**Recommendation:** Throttle updates:

```swift
private var lastProgressUpdate = Date.distantPast

// In the handler:
if Date().timeIntervalSince(lastProgressUpdate) > 0.1 {  // 10 updates/sec max
    lastProgressUpdate = Date()
    DispatchQueue.main.async {
        progress(estimatedProgress, statusMsg)
    }
}
```

---

#### 6.2 Synchronous Codable in Queue Persistence

**Location:** `QueueManager.swift` (saveQueue/loadQueue methods)

**Issue:** JSON encoding/decoding and file I/O happen synchronously on the main actor. For large queues, this can cause UI hitches.

**Recommendation:** Move to background:

```swift
private func saveQueue() {
    let jobs = self.jobs  // Capture current state
    Task.detached(priority: .background) {
        do {
            let data = try JSONEncoder().encode(jobs)
            try data.write(to: self.queueFileURL, options: .atomic)
        } catch {
            print("Failed to save queue: \(error)")
        }
    }
}
```

## Security Considerations

### 9. Input Validation

#### 9.1 Path Injection (Low Risk)

**Location:** `FFmpegWrapper.swift:109-114`

```swift
for videoFile in clip.videoFiles {
    args.append(contentsOf: ["-i", videoFile.path])
}
```

**Assessment:** Low risk because paths come from `FileManager.contentsOfDirectory`, not user input. However, if a P2 card contains maliciously named files, they're passed directly to FFmpeg.

**Recommendation:** Validate paths don't contain shell metacharacters:

```swift
guard !path.contains("$") && !path.contains("`") && !path.contains(";") else {
    throw FFmpegError.invalidInput("Suspicious characters in path")
}
```
