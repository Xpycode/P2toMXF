## 1. Critical Issues

### 1.1 Silent Clip Parsing Failures

**Location:** `P2CardParser.swift:53-56`
**Severity:** Critical | **Type:** Logic Error

```swift
for xmlFile in xmlFiles {
    if let clip = try? parseClipXML(at: xmlFile, contentsPath: contentsPath) {
        clips.append(clip)
    }
}
```

**Problem:** The `try?` silently swallows parsing errors. If a P2 card has 16 clips but 15 have XML issues (corruption, encoding problems, permission errors), the user sees 1 clip with no indication of failure.

**Impact:**
- Users may convert incomplete footage without knowing
- Debugging is impossible without error information
- Professional video workflows require reliable error reporting

**Fix:**
```swift
var clips: [P2Clip] = []
var parseErrors: [(file: URL, error: Error)] = []

for xmlFile in xmlFiles {
    do {
        let clip = try parseClipXML(at: xmlFile, contentsPath: contentsPath)
        clips.append(clip)
    } catch {
        parseErrors.append((xmlFile, error))
    }
}

// Report errors to user or log
if !parseErrors.isEmpty {
    let errorSummary = parseErrors.map { "\($0.file.lastPathComponent): \($0.error.localizedDescription)" }
    // Surface to ViewModel for user notification
}
```

### 1.2 Potential Deadlock in ThumbnailManager Semaphore

**Location:** `ThumbnailManager.swift:166-186`
**Severity:** Critical | **Type:** Concurrency Bug

```swift
private func acquireSemaphore() async {
    if activeExtractions < maxConcurrentExtractions {
        activeExtractions += 1
        return
    }

    await withCheckedContinuation { continuation in
        waitingContinuations.append(continuation)
    }
}
```

**Problem:** If a task acquires the semaphore but is cancelled before calling `releaseSemaphore()`, waiting tasks block indefinitely. The actor's isolation doesn't protect against cancellation-induced deadlocks.

**Scenario:**
1. 3 extraction tasks are running (max capacity)
2. 5 more tasks are waiting
3. All 3 running tasks get cancelled (user navigates away quickly)
4. `releaseSemaphore()` is never called
5. The 5 waiting tasks hang forever

**Fix:**
```swift
private func extractFrameWithSemaphore(from url: URL, atSeconds timestamp: Double) async -> NSImage? {
    await acquireSemaphore()
    defer { releaseSemaphore() }  // ALWAYS release, even on cancellation

    // Check cancellation after acquiring
    if Task.isCancelled { return nil }

    return await ffmpeg.extractFrame(from: url, atSeconds: timestamp)
}
```

### 1.3 Race Condition in Cancellation Flag

**Location:** `FFmpegWrapper.swift:49, 624-643`
**Severity:** Critical | **Type:** Data Race

```swift
private var isCancelling = false  // Plain Bool, no synchronization

func cancelConversion() {
    isCancelling = true  // Written from main thread
    // ...
}

// In terminationHandler (called on arbitrary thread):
let wasCancelled = self?.isCancelling ?? false  // Read from background thread
```

**Problem:** `isCancelling` is accessed from multiple threads without synchronization. This is undefined behavior in Swift and can cause:
- Cancelled conversions reporting as failures
- Non-cancelled conversions reporting as cancelled
- Memory corruption (rare but possible)

**Fix:**
```swift
private let cancelLock = NSLock()
private var _isCancelling = false

var isCancelling: Bool {
    cancelLock.withLock { _isCancelling }
}

func setCancelling(_ value: Bool) {
    cancelLock.withLock { _isCancelling = value }
}
```

Or use Swift Atomics:
```swift
import Atomics
private let isCancelling = ManagedAtomic<Bool>(false)
```

## 2. High Priority Issues

### 2.1 `@unchecked Sendable` Bypasses Compiler Safety

**Locations:**
- `FFmpegWrapper.swift:470-485`
- `BMXWrapper.swift:155-170`
- `VerificationService.swift:443-447`

```swift
private final class OutputCollector: @unchecked Sendable {
    private let lock = NSLock()
    private var _output = ""
    // ...
}
```

**Problem:** While the implementation uses `NSLock`, marking as `@unchecked Sendable` tells the compiler "trust me, this is thread-safe" - it won't catch future mistakes if someone modifies this class.

**Risk Level:** High if modified without understanding threading implications.

**Recommendation:**
1. Add extensive documentation explaining the threading contract
2. Consider using `OSAllocatedUnfairLock` (macOS 13+) which is faster
3. For new code, prefer actors:

```swift
actor OutputCollector {
    private var _output = ""

    func append(_ string: String) {
        _output += string
    }

    var output: String { _output }
}
```

### 2.2 MainActor Singleton Access Gap

**Location:** `QueueManager.swift:13-14`

```swift
@MainActor
class QueueManager: ObservableObject {
    static let shared = QueueManager()
```

**Problem:** `@MainActor` on the class ensures methods are called on the main thread from async contexts. However, `static let shared` can still be accessed synchronously from any thread:

```swift
// This compiles and runs on a background thread:
Task.detached {
    let manager = QueueManager.shared  // Accessing MainActor from background!
    print(manager.jobs.count)  // Data race!
}
```

**Fix:** Ensure all access goes through MainActor:
```swift
@MainActor
static let shared = QueueManager()

// For non-MainActor contexts:
nonisolated static func getShared() async -> QueueManager {
    await MainActor.run { shared }
}
```

### 2.3 File Handle Handlers May Persist After Process Ends

**Location:** `FFmpegWrapper.swift:516`, `BMXWrapper.swift:199`

```swift
errorPipe.fileHandleForReading.readabilityHandler = { [weak self] handle in
    // ...
}

process.terminationHandler = { [weak self] proc in
    outputPipe.fileHandleForReading.readabilityHandler = nil  // Only set here
    errorPipe.fileHandleForReading.readabilityHandler = nil
    // ...
}
```

**Problem:** If the process becomes a zombie or `terminationHandler` fails to fire, the readability handlers persist indefinitely, potentially:
- Holding references to `self` (memory leak)
- Continuing to process stale data
- Preventing file handle cleanup

**Fix:** Add defensive cleanup:
```swift
// After process.run():
do {
    try process.run()
} catch {
    // Clean up handlers on run failure
    outputPipe.fileHandleForReading.readabilityHandler = nil
    errorPipe.fileHandleForReading.readabilityHandler = nil
    throw error
}

// Consider adding timeout-based cleanup for zombie processes
```

### 2.4 Security-Scoped Resource Start/Stop Imbalance

**Location:** `QueueManager.swift` (multiple locations)

```swift
guard job.cardPath.startAccessingSecurityScopedResource() else {
    // ...
}
defer {
    job.cardPath.stopAccessingSecurityScopedResource()
}
```

**Problem:** Multiple clips from the same P2 card path result in nested `startAccessing`/`stopAccessing` calls. Apple's documentation states these must be balanced, but nested calls can cause:
- Resource access to stop prematurely
- Resource leaks if not properly balanced

**Fix:** Track accessed resources:
```swift
@MainActor
class QueueManager {
    private var accessedResources: Set<URL> = []

    private func startAccessingIfNeeded(_ url: URL) -> Bool {
        if accessedResources.contains(url) { return true }
        if url.startAccessingSecurityScopedResource() {
            accessedResources.insert(url)
            return true
        }
        return false
    }

    private func stopAccessingAll() {
        for url in accessedResources {
            url.stopAccessingSecurityScopedResource()
        }
        accessedResources.removeAll()
    }
}
```

## 3. Medium Priority Issues

### 3.1 Excessive UI Updates During Conversion

**Location:** `FFmpegWrapper.swift:558-573`

```swift
errorPipe.fileHandleForReading.readabilityHandler = { [weak self] handle in
    // ...
    DispatchQueue.main.async {
        progress(estimatedProgress, statusMsg)  // Called on every FFmpeg output line
    }
}
```

**Problem:** FFmpeg outputs progress lines 25-60 times per second. Each triggers a main thread dispatch and potentially View updates. This causes:
- High CPU usage from excessive redraws
- UI thread saturation during long conversions
- Battery drain on laptops

**Fix:** Throttle updates to ~10/second:
```swift
private var lastProgressUpdate = Date.distantPast

// In handler:
let now = Date()
if now.timeIntervalSince(lastProgressUpdate) > 0.1 {
    lastProgressUpdate = now
    DispatchQueue.main.async {
        progress(estimatedProgress, statusMsg)
    }
}
```

### 3.2 Synchronous Queue Persistence on Main Actor

**Location:** `QueueManager.swift` (saveQueue/loadQueue)

**Problem:** JSON encoding/decoding and file I/O happen synchronously on the MainActor. With large queues or slow storage, this blocks the UI.

**Fix:**
```swift
private func saveQueue() {
    let jobsToSave = self.jobs
    Task.detached(priority: .background) {
        do {
            let data = try JSONEncoder().encode(jobsToSave)
            try data.write(to: Self.queueFileURL, options: .atomic)
        } catch {
            await MainActor.run {
                self.log("Failed to save queue: \(error)")
            }
        }
    }
}
```

### 3.3 Unbounded Thumbnail Cache Growth

**Location:** `ThumbnailManager.swift:27-28`

```swift
private var cache: [UUID: ClipThumbnails] = [:]
private var pendingTasks: [UUID: Task<ClipThumbnails, Never>] = [:]
```

**Problem:** Cache grows indefinitely. `clearCache()` only called when loading new cards. Loading multiple cards accumulates memory.

**Fix:** Implement LRU eviction:
```swift
private let maxCacheSize = 100
private var accessOrder: [UUID] = []

func getThumbnails(for clip: P2Clip) async -> ClipThumbnails {
    // Track access order
    if let index = accessOrder.firstIndex(of: clip.id) {
        accessOrder.remove(at: index)
    }
    accessOrder.append(clip.id)

    // Evict if over limit
    while cache.count > maxCacheSize, let oldest = accessOrder.first {
        accessOrder.removeFirst()
        cache.removeValue(forKey: oldest)
    }

    // ... rest of implementation
}
```

### 3.4 Dead Code Path in Verification Fallback

**Location:** `VerificationService.swift:242-267`

```swift
private func getContainerInfoWithFFmpeg(
    fileURL: URL,
    logHandler: @escaping LogHandler
) async throws -> ContainerInfo {
    // ... always returns placeholder data:
    return ContainerInfo(
        format: fileURL.pathExtension.uppercased(),
        streams: 2,  // Hardcoded assumption
        duration: "--:--:--",
        durationSeconds: 0,
        estimatedFrames: 0,
        frameRate: 25.0
    )
}
```

**Problem:** This fallback never extracts real data from ffmpeg output. The stderr parsing is unimplemented.

**Impact:** If ffprobe is unavailable, verification uses meaningless placeholder data, potentially causing:
- Frame count mismatches marked as failures
- Incorrect duration reporting

**Fix:** Either implement proper stderr parsing or remove the fallback and require ffprobe.

### 3.5 Duplicated Tool Path Resolution

**Locations:**
- `FFmpegWrapper.swift:53-71`
- `VerificationService.swift:44-69`

Both files have nearly identical logic for finding ffmpeg/ffprobe:
```swift
var ffmpegPath: URL? {
    if let bundledPath = Bundle.main.url(forResource: "ffmpeg", withExtension: nil) {
        return bundledPath
    }
    let homebrewPaths = ["/opt/homebrew/bin/ffmpeg", "/usr/local/bin/ffmpeg"]
    // ...
}
```

**Fix:** Extract to shared utility:
```swift
struct BundledToolResolver {
    enum Tool: String {
        case ffmpeg, ffprobe, bmxtranswrap, mxf2raw
    }

    static func path(for tool: Tool, homebrewFallback: Bool = true) -> URL? {
        if let bundled = Bundle.main.url(forResource: tool.rawValue, withExtension: nil) {
            return bundled
        }
        guard homebrewFallback else { return nil }
        // ... homebrew paths
    }
}
```

## 5. Architecture Analysis

### 5.1 Overall Structure

```
P2toMXF/
├── P2toMXFApp.swift          # App entry, minimal
├── ContentView.swift          # Main UI container
├── ConversionViewModel.swift  # Primary state management
├── Models/
│   └── P2Clip.swift           # All domain models
├── Services/
│   ├── FFmpegWrapper.swift    # FFmpeg process management
│   ├── BMXWrapper.swift       # BMX process management
│   ├── QueueManager.swift     # Batch job queue
│   ├── P2CardParser.swift     # XML metadata parsing
│   ├── VerificationService.swift  # Output validation
│   ├── SpeedTracker.swift     # Time estimation
│   └── ThumbnailManager.swift # Thumbnail extraction
└── Views/
    ├── QueueListView.swift    # Queue panel
    ├── CardListView.swift     # Card sidebar
    ├── ProgressControlPanel.swift
    └── EstimateSheet.swift
```

**Strengths:**
- Clean MVVM separation
- Services are single-responsibility
- Models are Codable for persistence
- Actors used for concurrent thumbnail extraction

**Weaknesses:**
- ViewModels and Services are tightly coupled (not protocol-based)
- No dependency injection (difficult to test)
- Business logic mixed into Views (ClipRowView does thumbnail loading)

```
User Action
    ↓
```
